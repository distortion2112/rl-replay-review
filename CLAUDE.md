## What This Project Is

A Tauri v2 desktop app for reviewing Rocket League replays. Rust backend parses `.replay` files (via boxcars) and fetches stats from the ballchasing.com API. React/TypeScript frontend renders field visualizations, charts, and playback controls.

## Stack

| Layer | Tech |
|-------|------|
| Desktop shell | Tauri v2 |
| Backend | Rust (2024 edition) |
| Replay parsing | boxcars 0.13 |
| External API | ballchasing.com (stats + replay download) |
| Frontend | React 19, TypeScript, Vite |
| Styling | Tailwind CSS v4 |
| State | Zustand |
| Charts | Recharts |
| Icons | Lucide React |

## Architecture

```
src-tauri/src/
  commands.rs          <- Tauri command handlers (bridge to frontend)
  parser/
    replay_parser.rs   <- Single-pass boxcars parser with live actor state
    frame_data.rs      <- Frame-level data structures
  api/
    ballchasing.rs     <- ballchasing.com API client
    models.rs          <- API response types
  analysis/
    boost.rs           <- Boost usage analysis
    rotation.rs        <- Rotation pattern analysis
  benchmark/
    models.rs          <- benchmarks.json types (schema_version 1)
    loader.rs          <- Parse, schema check, rank lookup with nearest-tier fallback
resources/
  benchmarks.json      <- Per-rank stat distributions, generated by tools/benchmark-generator

src/
  App.tsx              <- Main app shell, tab routing
  components/
    field/             <- Canvas field renderer, heatmaps, trails
    charts/            <- Boost and movement charts
    stats/             <- Analysis panels, player comparison
    input/             <- API key setup, replay input, settings
    timeline/          <- Playback controls, scrubber, goal replays
  hooks/               <- useReplay, usePlayback, useKeyboard
  lib/                 <- Field math, heatmap logic, trail logic, Tauri command wrappers
  types/               <- TypeScript type definitions (replay, frames, analysis)
```

### Key Design Decisions

- **Two-tier data model**: Tier 1 = aggregate stats from ballchasing API (fast). Tier 2 = frame-by-frame from boxcars (detailed).
- **Live actor linkage, never whole-replay maps**: Actor IDs are recycled. A destroyed car's ID (goal reset, demo) is often reassigned to a *different* player's next car. All car→PRI, PRI→name and boost→car links are tracked per frame and dropped on actor deletion. A single car→player map built over the whole replay mislabels positions and drops players.
- **Car-PRI linking**: Uses `Engine.Pawn:PlayerReplicationInfo` on the car. Falls back to generic `ActiveActor` sniffing only if that attribute is absent from the replay's object table.
- **Boost tracking**: Maps `boost_component` to car actors live via `TAGame.CarComponent_TA:Vehicle`, not via pickup detection.
- **Sampled positions are projected to sample time**: Each rigid body updates every 1–3 network frames on its own schedule, so a raw position at a sample frame is 0–~70ms stale by a varying amount. The parser projects it forward by `linear_velocity × age` (capped at 0.25s). Without this, per-sample movement is uneven and interpolated playback pulses.
- **Replays have no frames during goal replays**: Frame times jump 2–9s after each goal. The frontend never interpolates across a gap > 0.5s, and playback skips across it.
- **Events resolve players at the moment they happen**: Touches and demos use the live car→player link, never a whole-replay map. A demolished car's Pawn PRI is unset in the demo frame itself, so events fall back to the car's last resolved player. Frames do not, so a wrecked car disappears immediately.
- **Demos**: Current replays send `DemolishExtended`, recorded on the victim's car. A respawned car may be re-created under the same actor ID *without* a delete, and its initial replication repeats the last demo. All state for re-created IDs is cleared, and demo attributes on a car created that frame are ignored. Demos with no attacker (e.g. post-goal explosions) keep `attacker_index: None`.
- **Benchmarks are generated, versioned data**: `resources/benchmarks.json` comes from `tools/benchmark-generator` (ballchasing stats, per player, tagged with that player's own rank). It is never hand-edited. It is regenerated per season, and the loader rejects unknown `schema_version`s. A missing tier falls back to the nearest one, and the response says so (`substituted`). `per_minute` stats must be divided by game minutes before comparing.
- **Demo gaps are expected**: A demolished player has no car actor for ~3s before respawn, so they are absent from those frames.

## Change Control

### Branch Strategy

```
main                   <- stable, always builds, only merged via PR
feature/<slug>         <- new features (feature/speed-chart)
fix/<slug>             <- bug fixes (fix/boost-parse-crash)
chore/<slug>           <- tooling, config, refactors (chore/add-clippy)
```

- **Never commit directly to `main`.** All changes go through a PR.
- Branch from `main`. Keep branches short-lived and focused.
- One issue per branch. One branch per issue.

### Commit Messages

```
<type>: <short imperative description>

feat: add per-goal mini-replay viewer
fix: handle missing PRI for disconnected players
chore: configure clippy lints
refactor: extract boost timeline into separate component
test: add parser tests for season 14 replays
docs: update CLAUDE.md with new architecture notes
```

Types: `feat`, `fix`, `chore`, `refactor`, `test`, `docs`

Keep commits atomic — one logical change per commit. Don't bundle unrelated changes.

### Pull Requests

1. Push your branch, open a PR against `main`
2. PR title: `<type>: <description>` (same as commit convention)
3. PR body must include:
   - **What** changed and **why**
   - `Closes #N` to auto-close the linked issue
   - Screenshots/recordings for visual changes
4. `npm run build` and `cargo build` must pass before merging
5. Squash merge preferred — keeps `main` history clean

### Issue Workflow

- Every non-trivial change starts with a GitHub issue
- Issues should be clear enough that someone (human or agent) can pick them up cold
- Use labels to categorize (see Labels section)
- When starting work: assign yourself, create a branch
- When done: PR closes the issue via `Closes #N`

## Code Quality Rules

### Rust (src-tauri/)

- `cargo build` must succeed with no errors
- No `unwrap()` on user-facing paths — use `Result` and propagate errors to the frontend via Tauri's error handling
- `unwrap()` is acceptable in tests and provably-safe internal logic
- Keep Tauri commands thin — they should delegate to parser/api/analysis modules
- New modules get a `mod.rs` that re-exports public items

### TypeScript (src/)

- `tsc --noEmit` must pass (strict mode is already on)
- No `any` types — use `unknown` and narrow, or define proper types in `src/types/`
- Components go in `src/components/<area>/` — don't dump everything in one folder
- Shared logic goes in `src/lib/`, hooks in `src/hooks/`
- Zustand stores: one store per domain concern, not one god store

### General

- Don't add dependencies without justification. This is a desktop app — bundle size matters less, but complexity still matters.
- Don't refactor code unrelated to your current issue. File a separate issue if you spot something.
- Don't add speculative features. If it's not in an issue, it doesn't get built.

## Agent Startup Checklist

Run through this list at the **start of every session**, in order:

1. **Read this file.** You're doing it now. Good.
2. **Check GitHub Issues.** Look for issues assigned to you or unassigned issues labeled `priority:high` or `priority:medium`. This is your work queue.
3. **Check for handoff notes.** Look in `/home/distortion2112/.claude/projects/-home-distortion2112-code-rl-replay-review/memory/` for any `handoff.md` or recent updates to `MEMORY.md`. Previous agents leave context there when a session ends mid-work.
4. **Check open PRs.** If there's a PR in progress from a previous session, pick it up — don't start a duplicate branch.
5. **Check recent commits on `main`.** Run `git log --oneline -10` to understand what just landed and avoid conflicts.
6. **Pick one issue.** Assign yourself, create a branch (`feature/`, `fix/`, `chore/`), and start work. One issue at a time.

If there are no issues, no handoffs, and no PRs in progress — ask the user what to work on. Don't invent work.

### Before Ending a Session

If you're mid-task and the session is ending:

1. **Commit and push** your work-in-progress branch (even if incomplete).
2. **Write a handoff note** to `memory/handoff.md` with:
   - What issue you were working on
   - What's done, what's left
   - Any blockers or decisions needed
   - The branch name
3. **Update the issue** with a comment summarizing progress.

## Agent Guidelines

When working as an AI agent on this project:

1. **Don't make sweeping changes.** Small, focused PRs. If a change touches more than ~5 files across unrelated areas, break it up.
2. **Don't "improve" code you're not working on.** No drive-by refactors, no adding comments to untouched files, no reformatting.
3. **Test your changes.** At minimum: `cargo build` for Rust, `npm run build` for TypeScript. Run the app if you can.
4. **Update this file** if you make architectural decisions. Add them to the Key Design Decisions section.
5. **Coordinate via issues.** If another agent is working on something, don't start a conflicting branch. Check what's assigned.
6. **Create an issue first** if you identify new work that needs doing. Then branch, implement, PR.
